# 通用开发规则（DEVELOPMENT_RULES）— AI-SDLC v1.0

> **权威定义**：本文件是跨项目通用开发规则的唯一权威定义。其他文档通过路径引用，不复制全文。  
> 项目专属业务规则见 `DMS_V1.0_MiMo_Development_Spec.md` 与 `AGENTS.md`。两者冲突时见 `AGENTS.md` 规则优先级。  
> 本版依据 `docs/AI_SDLC_FINAL_VERIFICATION_REPORT.md` 缺口 G1～G6 修订（2026-10-14）。

## 1. 每次开启任务

1. 确认工作区位于项目根目录；若不是，停止修改并报告。
2. 读取 `AGENTS.md`、`.ai/PROJECT_CONTEXT.md`、`.ai/MILESTONES.md`、`.ai/DECISIONS.md` 与最近阶段验收报告（以实际存在的文件为准）。
3. 检查 Git 状态与未提交更改；保护现场，不得覆盖、回滚或清理用户修改。
4. 制定本任务计划（范围、依赖、拟改文件、验证命令、验收标准）后再实施。

## 2. 代码与文档

- 优先编辑现有文件，避免无意义新建；不随意移动/重命名已有文件。
- 小步修改，同步更新测试与相关文档。
- 通用规则只保留一份权威定义，其他文档通过相对项目根目录的路径引用。
- 不得用硬编码数组、模拟接口、假成功提示代替真实数据读写。
- 不因修复局部问题覆盖用户手工修改、现有配置或其他阶段成果。
- 注释只写非显然的 WHY；不写流水账注释。

## 3. 测试与验证

### 3.1 必须实际执行

- 修改后必须**实际运行**适用检查（lint / typecheck / test / build / 迁移校验等）。
- **未实际执行的测试必须明确标记为「未执行」或「未测试」**，不得编造通过记录、截图或 Git 提交信息。
- Web 前端涉及页面或交互修改时，必须使用 **Playwright** 执行真实浏览器测试，并保存截图、测试命令和结果。
- 关键业务路径至少覆盖：重复工号、重复床位、并发预留、同员工重复入住、调宿/退宿竞争、离职未退宿、越权访问、导入异常。
- 完成阶段时记录：测试命令、关键输出、结果、环境版本；不能只报“已通过”。

### 3.2 统一测试结果口径（G2）

所有测试项、需求映射与场景矩阵**必须**使用下列五种状态之一，不得自造其他结论词：

| 状态 | 含义 |
|---|---|
| **通过** | 实际执行且结果符合预期 |
| **失败** | 实际执行且结果不符合预期 |
| **跳过** | 主动跳过（须写明原因；非因失败而绕过） |
| **环境阻塞** | 因环境/依赖/权限等外部条件无法执行（须写明阻塞原因与可复现步骤） |
| **未执行** | 本次未安排执行（含「未测试」） |

强制规则：

1. **不得**将「跳过」「环境阻塞」「未执行」计入「通过」数量或“通过率”。
2. 存在**未解决 P0 缺陷**时，阶段验收**必须**判定为不通过。
3. 测试未完整执行时，**不得**声明“全量通过”“全部通过”等同义表述。
4. 汇总统计须分列通过 / 失败 / 跳过 / 环境阻塞 / 未执行，并可对账到明细行。

### 3.3 缺陷证据最低字段（G3）

每条缺陷（含自检发现与复核发现）必须记录：

1. **测试入口**（页面路由 / API / 测试用例名 / 命令）
2. **复现步骤**
3. **预期结果**
4. **实际结果**
5. **证据路径**（日志、截图、trace、视频等）
6. **对应代码版本**（Git commit SHA；无基线时写「未建立 Git 基线」，见 §9）

模板：`.ai/acceptance/BUG_TEMPLATE.md`。

## 4. 缺陷分级（G1）

缺陷级别根据**实际影响**及**可复现证据**判定；同级争议时就高不就低，并记入 `.ai/DECISIONS.md` 或阶段报告。

| 级别 | 名称 | 判定要点 | 验收影响 |
|---|---|---|---|
| **P0** | 阻断级 | 数据丢失、数据一致性破坏、严重越权、核心业务无法完成 | **禁止验收通过**；须修复并回归后方可过门 |
| **P1** | 高优先级 | 重要功能故障、可靠性缺陷、可导致错误业务结果的问题 | 原则上**必须修复后验收**；延期须用户明确批准并记录风险 |
| **P2** | 中优先级 | 非核心功能异常、局部 UI/UX 缺陷 | 允许经**明确确认**后延期修复，须写入遗留清单与计划 |
| **P3** | 低优先级 | 轻微显示问题、文档问题、非关键优化建议 | 可带记录验收；建议纳入下阶段清理 |

补充口径：

- 「严重越权」包括：跨数据范围读取/导出敏感数据、绕过权限写入、提权。
- 「数据一致性破坏」包括：重复占用床位/住宿、历史被覆写、计数与权威记录不符且无法解释。
- 单测/接口测/UI 测发现的同一根因缺陷只计一条，但须列出全部证据入口。

## 5. 阶段门禁

- 阶段自检完成后提交 GPT Web 复核，**不自动**启动下一阶段。
- 修复后须跑相关测试与核心回归；必要时重复数据库迁移与备份恢复演练。
- 未做完整检查时不得写“全量通过”（见 §3.2）。
- 门禁结论使用：**通过 / 不通过 / 有条件通过**；有条件通过必须列出未关闭项与责任人。

## 6. AI-SDLC 阶段工作流

```
GPT Web 编写阶段指令 → MiMo 开发 → MiMo 自动化自检 → GPT Web 复核 → GitHub 提交阶段版本
```

1. **GPT Web** 编写阶段指令（可用 `.ai/prompts/STAGE_START_TEMPLATE.md` 或 `M01_START.md`）。
2. **MiMo** 按指令开发，实施并验证，更新计划/决策/验收文档。
3. **MiMo 自动化自检**：运行测试；涉及 Web UI 时用 Playwright 真测并留存证据。
4. **GPT Web 复核**（独立验收，不等于自检结论）。
5. **GitHub 提交阶段版本**（由用户/复核方授权执行；Tag 见 §10）。
6. 全部阶段结束后，由 **ChatGPT Mac Work** 在隔离测试环境进行最终 UI/UX 与端到端验收（模板：`.ai/audit/FINAL_WORK_ACCEPTANCE.md`）。

## 7. Git 与发布

- 未经用户明确授权，不执行 `commit` / `push` / `force push` / `tag`。
- 不重写已发布历史；不擅自部署到生产环境。
- 不删除既有业务表、记录或 Docker volume；破坏性迁移需明确授权与备份恢复方案。
- 版本标记约定见 §10。

## 8. 安全与数据

- 不在代码、日志、报告中泄露密码、Token 或真实凭据。
- 测试/自检使用隔离测试库与合成数据，不向正式库执行写测试。
- 上传/导出注意公式注入等输入输出安全。
- 不得关闭权限检查、数据库约束或测试来“使功能通过”。

## 9. 版本与测试证据基线（G3）

阶段验收报告（模板：`.ai/acceptance/ACCEPTANCE_TEMPLATE.md`）**必须**包含下列环境基线字段；无法获取时写「不适用」或「未获取」并说明原因，**禁止**留空充数或虚构。

| 字段 | 说明 |
|---|---|
| Git commit SHA | `git rev-parse HEAD` |
| 当前分支及工作区状态 | 分支名 + `git status --short` 摘要（干净/脏） |
| Docker Compose 项目名称 | `docker compose ls` / 项目名 |
| Docker 镜像版本或 digest | 镜像 tag 或 `digest`（可获取时） |
| Alembic 当前 revision | `alembic current` |
| Python / Node.js 版本 | `python -V` / `node -v` |
| 浏览器及操作系统版本 | Playwright 浏览器版本 + OS |
| 测试环境与数据库隔离情况 | 是否隔离测试库、库名/标识（勿写真实凭据） |

规则：

1. **尚未建立 Git 提交历史**的环境，一律标记为 **「未建立 Git 基线」**，**禁止虚构 SHA**。
2. 每条缺陷的「对应代码版本」与上表 SHA 一致；跨版本对比时写明各自 SHA。
3. 测试记录还应含：执行命令、关键输出摘要、结果状态（§3.2）、证据路径。

## 10. 版本标记约定（G4）

阶段验收成功（含 GPT Web 复核通过）后，**建议**按语义打 Tag：

| 场景 | Tag 格式 | 示例 |
|---|---|---|
| 阶段验收通过 | `m<N>-accepted` | `m1-accepted`、`m2-accepted`、`m3-accepted` |
| 正式版本 | 语义化版本 `vX.Y.Z` | `v1.0.0` |

强制规则：

1. Git Tag **必须**指向**实际完成复核**的提交，不得打在未验收或工作树混乱的变更上。
2. **不得覆盖、移动或删除已有 Tag**；需要修正时新增 Tag 并在决策记录中说明。
3. **未经用户明确授权，不得自动执行 `commit`、`tag` 或 `push`。**
4. 打 Tag 前检查：工作树是否干净、验收结论是否为通过、报告中的 SHA 是否与 Tag 提交一致。

## 11. 测试期间版本冻结（G5）

执行阶段验收 / 自检回归期间：

1. **暂停**其他 AI 窗口对**同一源码目录**的并发修改。
2. **禁止**其他任务操作当前测试数据库（含迁移、清库、批量写入）。
3. **记录**测试开始与结束时的 Git 状态（SHA + `git status --short`）。
4. 若测试期间代码发生变化（开始/结束 SHA 不一致，或工作树由净变脏），**必须重新评估**该批测试结果的有效性；必要时在新基线上重跑。
5. 涉及数据写入的自动化测试必须在**独立测试环境**执行（见 §8）。

## 12. 重大变更控制（G6）

涉及以下事项时，**必须**先形成书面变更建议（写入 `docs/DECISIONS.md` 或阶段指令/计划）并**取得用户批准**后实施：

- 技术栈调整
- 数据库破坏性迁移
- 核心业务规则修改
- 认证与数据权限模型修改
- 删除已有功能
- 改变已验收的接口契约
- 大规模重构

**严禁**为了让测试通过而：

- 删除失败的测试
- 跳过重要断言
- 弱化数据库约束
- 绕过权限校验
- 修改原始业务需求
- 伪造测试报告

上述禁止项与 §2/§3/§8 一致；发现为过门而篡改测试或规格的，视为 P0 流程缺陷，阶段不得通过。

## 13. 通用禁止事项

- 覆盖、回滚或清理用户未提交更改。
- 删除已有验收报告，或将已完成阶段重置为未开始/待开发。
- 凭空编造实现、测试结果、截图、SHA 或提交记录。
- 在未获授权时开始新业务阶段开发。
- 以微服务改造等无关重构替代当前任务。
- 将「跳过 / 环境阻塞 / 未执行」记为「通过」，或在存在未关闭 P0 时判定阶段通过（见 §3.2、§4）。
- 未经用户批准实施 §12 所列重大变更，或为过门执行 §12 禁止行为。
